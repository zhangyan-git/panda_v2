# 开放平台接入规范

这份文档是给**合作方**看的：你把请求发到我们的开放接口之前要准备什么、每个请求怎么签、
失败了怎么读那句话、以及哪些事我们**没有**做（那一条同样重要，别按猜的写代码）。

内部实现（验签中间件的九道关卡、限流、调用日志）在 `backend/services/partner-service/`；
那份代码里的注释是这份文档的来源，两者不一致时以代码为准，并把这份文档改过来。

---

## 一、接入前：两步，都在我们后台做

1. **建合作方**（我们这边的运营做）：得到一个 `code`，它是你的身份标识，建成后不可修改。
2. **签发 API 密钥**：一对值——`apiKey`（对应请求头 `X-API-Key`）与 `secret`（用来算签名）。

> ⚠️ **`secret` 只在签发的那一次响应里出现一次。** 我们的库里存的是密文信封，之后无论刷新页面、
> 看列表还是问我们要，拿到的都只有掩码（形如 `he83…4qo2`）。丢了没有「再查一次」这条路，
> 只能停用那一把、重新签一把。**请在收到它的当场存进你自己的密钥管理里。**

同一把密钥上还能配三样，都由我们的运营设置、你可以要求调整：

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 有效期 | 不过期 | 到期后该密钥自动被拒（我们每次请求都现查，不需要谁去手动停用） |
| 来源 IP 白名单 | 空 = **不限制** | 填了之后不在名单里的请求一律被拒。注意空白的语义是「不限制」，不是「全拒」 |
| 每分钟额度 | 60 次/分钟 | 按**密钥**计。超了回 429 |

合作方与密钥都有启停。**停用合作方，它名下所有密钥当场全部失效**（包括状态还显示启用的那些）。

> ⚠️ **密钥上今天没有任何「能操作哪些设备」的限制。** 只要一把密钥有效，它就能对**我们库里
> 任何一台已登记的设备**发回执——我们这边不做设备归属校验（完整说明见第七节第 9 条）。如果你
> 需要的是「一把密钥只能碰自己名下的机器」，那个能力今天**不存在**，请只对自己名下的设备调用。

## 二、每个请求要带的四个头

```
X-API-Key:    {签发时给你的 apiKey}
X-Timestamp:  {当前 Unix 秒，十进制整数}
X-Nonce:      {随机串，每个请求一个，见第四节}
X-Signature:  {见第三节，hex 小写}
```

`X-API-Key` **本身不参与签名**（它是身份，不是报文内容）。`X-Timestamp` / `X-Nonce` 参与。

---

## 三、签名怎么算

### 3.1 待签参数集

把下面这些键值收进一个集合：

| 键 | 取值 |
| --- | --- |
| `timestamp` | `X-Timestamp` 头的值，**原样**（你签的就是你发出去的那一串，我们不做重新格式化） |
| `path` | 请求路径，如 `/v1/openapi/device/sync-order`（**不含域名与 query**） |
| `method` | `GET` / `POST`，**大写** |
| `nonce` | `X-Nonce` 头的值，原样 |
| 每个 query 参数 | 键名即参数名，值是该键的**第一个**值（同名出现多次时取第一个） |
| body 的每个顶层键 | 见下面这条 |

**body 怎么进串**（JSON 一层打平，不递归）：

- 字符串值 → 原样；
- 其他值（数字、布尔、数组、嵌套对象）→ 它们的**紧凑 JSON 形式**：`1500`、`false`、
  `["a","b"]`、`{"b":1,"a":2}`。不要加空格、不要带换行。

> 用 JavaScript 的话，`JSON.stringify(value)` 就是这个形式（`JSON.stringify(1500)` → `"1500"`，
> `JSON.stringify(false)` → `"false"`）。用别的语言请确认整数不会变成 `1500.0`——那会签出
> 一个对不上的串。

### 3.2 拼串

1. **丢掉值为空串的参数**（`remark=""` 这类不进串）；
2. 剩下的键按**字节升序**排序（等价于 ASCII 升序）；
3. 拼成 `k=v`，用 `&` 连接；
4. **末尾追加上 `&secret={你的 secret}`**（即使前面是空的，这个 `&` 也在）。

### 3.3 摘要

```
X-Signature = hex(HMAC-SHA256(key = secret, message = 上面那个串))
```

hex **小写**。

### 3.4 完整示例

`secret = demo-secret-replace-me-0123456789`，请求：

```
POST /v1/openapi/device/sync-order
X-Timestamp: 1789646082
X-Nonce: 9f8c1d2e3b4a59687766554433221100
body: {"thirdPartyOrderNo":"TP20260917000001","deviceSerial":"SN-0001","drinkCode":"A01","amount":1500,"brewFailed":false,"remark":""}
```

待签串（`remark` 是空串，被丢掉了）：

```
amount=1500&brewFailed=false&deviceSerial=SN-0001&drinkCode=A01&method=POST&nonce=9f8c1d2e3b4a59687766554433221100&path=/v1/openapi/device/sync-order&thirdPartyOrderNo=TP20260917000001&timestamp=1789646082&secret=demo-secret-replace-me-0123456789
```

```
X-Signature: b78924693a0359ea913adf078805591294afb32ff6661b1a8e5fdb24b7eed2cc
```

同一个 `secret`、`timestamp`、`nonce` 下的查询接口：

```
GET /v1/openapi/member-price-entitlement?userId=0f0a3b1c-1111-2222-3333-444455556666
```

```
method=GET&nonce=9f8c1d2e3b4a59687766554433221100&path=/v1/openapi/member-price-entitlement&timestamp=1789646082&userId=0f0a3b1c-1111-2222-3333-444455556666&secret=demo-secret-replace-me-0123456789
X-Signature: c9e0dc698aa3110811b795e0f6ffc7d869cf7c2de2e759451fe52ffef2e13848
```

> 这两个示例可以直接当自测用例：如果你的实现对这两组入参算不出上面这两个签名，先修实现，
> 别急着发请求。

### 3.5 两件要提前知道的事

- **签名是规范化过的，不是逐字节的。** 重排 JSON 键的顺序、改缩进或空格，签名照样对得上
  （我们按打平后的键值算）。所以「签名通过了」保证的是**内容没被改**，不是**字节没被改**。
- **每个方法都签 body**，不只 POST。这是有意的：只签 POST 的话，PUT/PATCH 上的报文就完全
  在签名之外，改掉它签名照样对得上。今天这两条接口是 GET 与 POST，但你的实现别把这一条
  写死成「只有 POST 才打平」。

## 四、时间窗与 nonce

- `X-Timestamp` 必须落在我们的时钟 **±5 分钟**之内（双向：太旧和太新都拒）。请给服务器配 NTP。
- `X-Nonce` **每个请求都要换一个新的随机串**，且我们会在 Redis 里去重，TTL 也是 5 分钟。
  同一个 nonce 在窗口内重发 → **401**。
- nonce 之所以也进签名，是为了挡住「抓到你的请求、把 nonce 换个新的再重发」——那样做必须
  重新签，而重新签需要 secret。

## 五、响应信封与错误

### 5.1 成功

```json
{ "success": true, "data": { ... } }
```

### 5.2 失败

```json
{ "success": false, "errorCode": "UNAUTHORIZED", "errorMessage": "unauthorized" }
```

**对外的 `errorMessage` 是固定的一句句，不含任何内部细节。** 这是有意的：把「密钥不存在」
与「签名不对」分开回，等于给攻击者一台枚举机。真实原因只写在我们自己的调用日志里（那一列
在后台可以按合作方与时间段查）。

### 5.3 状态码

| 状态码 | `errorCode` | 你该做什么 |
| --- | --- | --- |
| 200 | — | 成功（**注意：幂等命中也是 200**，见 6.4） |
| 400 | `INVALID_REQUEST` | 报文要改。可能是 JSON 格式不对、多了我们不认识的字段（我们不忽略未知字段，直接 400）、或字段内容不成立 |
| 401 | `UNAUTHORIZED` | 凭据或签名有问题：密钥不存在/被停用/过期、合作方被停用、来源 IP 不在白名单、时间戳超窗、nonce 重放、签名不匹配。**别原样重投**，先按上面的顺序自查 |
| 403 | `FORBIDDEN` | 报文本身没写错，是**报文里那个值**我们不认：取货码那条的码不对。别去核对自己的拼写 |
| 404 | `NOT_FOUND` | 你问的东西我们没有。两条设备回执：这台机器还没在我们这里登记 |
| 405 | `METHOD_NOT_ALLOWED` | 动词用错了（带 `Allow` 头告诉你该用哪个） |
| 409 | `CONFLICT` | 我们**明确**的结论，但请求没写错：取货码那条的设备余额不够。**别重投**——重投一百次结果一样 |
| 413 | `INVALID_REQUEST` | 报文超过 1 MiB |
| 429 | `TOO_MANY_REQUESTS` | 超过每分钟额度。**这一条是唯一要「等一下」的**，响应带 `Retry-After`（秒） |
| 500 | `INTERNAL_ERROR` | 我们的错 |
| 503 | `SERVICE_UNAVAILABLE` | 我们暂时没答上来（下游不可用）。**可以原样重投**——这几条接口都是幂等的 |

**4xx 与 5xx 的分界是有意义的**：4xx 表示我们**明确**不受理这份请求，重投一百次结果一样；
5xx 表示我们没有结论，等一会儿再来。

## 六、三条接口

### 6.1 查会员权益（只读）

```
GET /v1/openapi/member-price-entitlement?userId={用户 ID}
```

我们这个 `userId` 由你侧先前与我方约定（它是我们平台内的用户标识）。

响应 `data`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `userId` | string | 原样回显（我们归一成小写 uuid 之后的形式），批量查询时用它对齐 |
| `partnerId` | string | 发起这次查询的合作方。**这是回显，不是下游的事实**，用途是让你能与自己的调用日志对上 |
| `active` | bool | 此刻是不是有效会员（冻结中的是 `false`） |
| `grantsMemberPrice` | bool | 此刻能不能**直接**按会员价算（只有年度会员为 `true`） |
| `memberPriceMode` | string | `auto`（本人自动享）/ `coupon`（靠会员价体验券）；不是会员时是空串 |
| `planCode` / `planName` | string | 成交快照上的套餐（我们后台改过套餐名不影响这两个值） |
| `expireAtUnix` | int64 | 到期时间（Unix 秒）；不是会员时是 `0` |

> `active=true` **不等于** `grantsMemberPrice=true`：连续包月的会员靠一张会员价体验券来享受
> 会员价，那一刻 `active` 为真而 `grantsMemberPrice` 为假、`memberPriceMode` 是 `coupon`。
> 只按 `active` 判会员价的对接方会算错这一档。

### 6.2 设备刷卡回执（写）

线下刷卡机**先收钱、后出杯**。钱在机器上收过之后，把这次成交同步给我们，我们落一张已支付
的订单。**这一条不需要、也不会发起任何支付**——那笔钱不是我们收的。

```
POST /v1/openapi/device/sync-order
```

请求体（多一个键就是 400，我们不做静默忽略）：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `thirdPartyOrderNo` | string | 是 | **你的单号，也是幂等键**。空串直接拒 |
| `deviceSerial` | string | 是 | 机器自己认识的那个编号。门店与设备由我们从它推出来，你不用给门店 |
| `drinkCode` | string | 是 | 机器报的饮品编号。**不是我们这边的 uuid**（机器不可能知道我们的主键） |
| `amount` | int64 | 否 | 成交金额，单位**分**。为 `0` 时我们回退到饮品的目录价 |
| `brewFailed` | bool | 否 | `true` = 出饮失败。**失败照样建单**（钱收了），履约那一格标成失败留人工 |
| `remark` | string | 否 | 备注，我们拼在「设备刷卡购买：」之后 |

响应 `data`：

| 字段 | 说明 |
| --- | --- |
| `orderId` | 我们这边的订单 uuid（排查入口） |
| `orderNo` | 我们的订单号（对账用） |
| `created` | `true` = 这次真的建了单；`false` = **幂等命中**，返回的是既有那张单 |

### 6.3 取货码回执（写）

顾客在机器上敲取货码、我们这边扣款出杯。与上一条的差别只有**钱的来源**：刷卡机那笔钱在机器上
收过了，这一杯从**这台设备的咖啡余额**里扣（余额由我方运营充值）。扣成功就是成功，同样
**不发起任何支付**、没有 pending 可等，落一张已支付的订单。

```
POST /v1/openapi/device/pickup
```

请求体（多一个键就是 400）：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `thirdPartyOrderNo` | string | 是 | **你的单号，也是幂等键**。空串直接拒。**每次取货都要是一个新的、唯一的值**——两台机器上先后发生的两次取货共用一个单号，第二次会被当成重投，那一杯就白出了 |
| `deviceSerial` | string | 是 | 机器自己认识的那个编号。钱从这台设备的余额里扣，门店也由它推出来 |
| `drinkCode` | string | 是 | 机器报的饮品编号，**不是我们这边的 uuid** |
| `pickupPassword` | string | 是 | 顾客敲的取货码。我们**只转不判**：比对在持有那一列的咖啡机域里做 |
| `remark` | string | 否 | 备注，我们拼在「取货码购买：」之后 |

**没有 `amount`**，这是与上一条**相反**的一处：这一杯的价由我们定（取货码价，没配则回落到目录
价）。刷卡机那条采信设备报的价，是因为钱在机器上收过了；这条路的钱是从我们自己的余额里扣的，
收对方报的价等于让它决定我们扣多少。

响应 `data` 与上一条逐字相同：`orderId` / `orderNo` / `created`。

这条路上有四个**确定**的拒绝档（`errorCode` 见 5.3 那张表，这里写的是 `errorMessage` 那一句）：

| 状态码 | `errorMessage` | 含义 |
| --- | --- | --- |
| 400 | `the pickup request is invalid` | 报文缺字段、饮品编号匹配不到、这一杯没配价、或者**这个单号已经属于另一类设备单**（见 6.4） |
| 403 | `pickup code is not accepted` | 取货码不对（机器没配过码也是这一句） |
| 404 | `device is not registered` | 序列号没登记（与刷卡回执同一句话） |
| 409 | `device balance is not enough` | 这台设备的余额不够这一杯 |

四档**一行都不写**：余额不动、没有余额流水、也没有订单。

- 409 是**结论**不是故障：让顾客去充值或换一杯，**别原样重投**；
- 503（`pickup service is unavailable`）才是故障，**可以原样重投**——同一笔取货重投不会扣两次。

### 6.4 幂等与重试

**按 `thirdPartyOrderNo` 幂等。** 重投不会多出一张单，命中时 HTTP 仍是 **200**，只是
`created=false`。请按这个字段区分「新建了」与「重投了一次」。

**6.2 与 6.3 两条接口共用一个单号空间。** 这是硬约束，不是建议：一个
`thirdPartyOrderNo` 只能属于**一条**接口。拿已经用在刷卡回执上的单号去打取货码，我们会回 400
（`the pickup request is invalid`），反过来也一样（`the device order request is invalid`）。
理由是我们这边这一列上只有一个唯一索引，它只认单号、不知道这个号是从哪条接口进来的——所以
「这个号我用过没有」这件事在我们这里是**跨两条接口**的，请你也按一个空间来生成。用一个号打
两次不同类型的回执不是重投，是一次**确定的拒绝**，重投不会变好。

- 网络超时 / 503 / 429 → **原样重投**（幂等，不会多出单）；
- 400 / 404 → 改报文或先登记设备再投，别原样重发；
- 401 → 先自查签名与时钟，别重投。

### 6.5 出饮失败了怎么办

`brewFailed=true` 时我们**照样落单**并把履约标成失败，由我们的人工处理。你那边不需要做
任何补偿动作，也不要把这一单当失败重投（重投会命中幂等，什么都不会变）。

## 七、我们**没有**做的事（已知缺口，别按猜的写代码）

这些不是「将来会有」，是**明确记在案的边界**，读的时候请把它们当成契约的一部分：

1. **刷卡回执的金额我们不对账。** 你报 `amount` 是 `510`、而饮品目录价是 `1990`，我们记的就是
   `510`，不会比对、不会拒绝、也没有事后核对。金额的基准在你（机器/厂商）那边，不在我们这里。
   `amount` 报 `0` 才回退目录价。（**取货码那条没有这个字段**：那一杯的价由我们定，见 6.3。）
2. **设备价高于目录价时，订单上看不出「贵了」。** 我们订单的金额恒等式中优惠不能为负，
   所以那一档会被记成 `original = payable`、优惠为 0。
3. **`paid_at` 是我们收到回执的时刻**，不是机器上真正收钱的那一刻（回执里没有那个时间戳）。
   两者只差一次网络往返，但要知道它不是成交时间。
4. **合作方身份不会写进订单。** 订单上只有设备与金额，没有 `partnerId`。要追「这笔是哪家发的」，
   走我们的调用日志（按 API 密钥 → 合作方，日志里有请求报文与时间）。
5. **调用日志目前没有保留期**：会长久留着。将来有清理策略时会提前通知。
6. **我们没有开放「改单 / 撤单 / 退款」的接口。** 设备单是既成事实的登记，不可通过开放接口
   修改。真出了需要冲正的情况，请联系我们的对接人走人工。
7. **取货码那条我们不知道杯子有没有出成。** 出杯由机器自己完成、顾客就站在机器前，我们这边
   的履约停在「待履约」那一格——那条路径里**没有** `brewFailed` 这样的字段，也不采信任何
   出杯结果。真出了「扣了钱没出杯」的情况，请联系我们的对接人走人工（与上一条同一条路）。
8. **扣款只有一次机会。** `thirdPartyOrderNo` 在这条路上唯一的含义就是幂等键：同号重投不会
   扣第二次（返回既有那张单）。反过来说——**两台机器上先后发生的两次真取货共用一个单号，
   第二杯不会被扣钱**，而订单也只会有一张。这个键必须由你保证唯一。
9. **我们不校验「这台设备是不是你的」。** 开放接口这一层验的是「这把密钥有没有效」，验完就把
   报文交给下游；`deviceSerial` 属于谁，这条路上没有任何判断。也就是说：一把有效密钥可以对
   **任何一台已登记的设备**发刷卡回执，也可以对任何一台设备发起取货码扣款——后者扣的是**那台
   设备**的余额。这是**已知边界**，与第 4 条同源（订单上也没有合作方身份）：设备厂商主数据与
   设备归属在咖啡机域，那一块还没做，所以我们这边没有能拿来比对的数据。等它落地时会在这一层
   补上（比对的是密钥解出来的合作方身份，不是你报文里填的字段——身份永远不来自报文）。在那之前
   请只对自己名下的设备调用。

---

## 八、自测建议（按这个顺序）

1. 用第三节那两组示例入参算签名，对上文档里的值——**先证明算法对了**，再碰网络。
2. 打一条查询接口。正确签名应当 200；把 body 或 query 改一个字符、签名不动，应当 401。
3. 故意用一个 10 分钟前的时间戳 → 401；用同一个 nonce 连发两次 → 第二次 401。
4. 设备回执连发两次（同一个 `thirdPartyOrderNo`）→ 第二次 200 且 `created=false`。
5. 检查时钟：跑一天之后再看时间戳是否仍在 ±5 分钟内（没有 NTP 的机器漂移会先让这一步失败，
   而症状是「昨天还好好的，今天全 401」）。

### 附：常见的 401 但签名没错

- **时钟没同步**（最常见）；
- **`X-Nonce` 复用了**（同一个请求重发、或压测工具把同一个报文并发打了很多次）；
- **签了 query 但发的时候漏了 / 顺序变了**（query 参与签名，`?a=1&b=2` 与 `?b=2&a=1`
  签出来一样，但**少一个参数就不一样**）；
- **body 里的数字序列化成了 `1500.0`**；
- **`path` 里带了 query 或域名**（只签路径本身）；
- **换了密钥却没换配置**（我们这边停用旧钥、签发新钥之后，你的 `secret` 要跟着换）。
